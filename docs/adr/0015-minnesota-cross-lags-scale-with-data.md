# MinnesotaPrior cross-lags always scale by σᵢ/σⱼ

`MinnesotaPrior.build_priors` on the PyMC path ignored the data: `B_sigma[i, j]` for the coefficient on variable `j`'s lag in equation `i` was a pure function of `tightness`, `decay`, and `cross_shrinkage`, with no reference to the units either variable was measured in. `build_priors` now takes a required keyword `sigma`, the per-variable AR(1) residual standard deviation (`impulso._conjugate.ar1_residual_sd`), and multiplies every cross-lag standard deviation by `sigma[i] / sigma[j]` — the classical Litterman ratio. Own lags (`i == j`) are untouched, since the ratio is 1 there for any finite nonzero `sigma[i]` — the exactly-zero case is a real failure mode, not just a caveat; see Consequences. `VAR.build_in_model` resolves `sigma` once (`ar1_residual_sd(endog)`, or the caller's `endog_scales` on the embedded path, ADR-0016) and passes the same array to `Prior.build_priors` and to the exogenous-coefficient prior (`_exog_prior_sigma`), so the two no longer disagree about what "the data's scale" means. This is always on: there is no flag to switch it off.

Three things motivate this, in order of weight:

1. **It is the textbook Minnesota prior.** Doan, Litterman & Sims (1984) and Litterman (1986) define the cross-lag standard deviation with a `sigma_i / sigma_j` term built in; `impulso.priors.MinnesotaPrior` shipped without it, which is a gap in the implementation, not an alternative formulation. `docs/explanation/minnesota-prior.md` and `docs/tutorials/minnesota-prior.py` said so explicitly, in a warning admonition that this ADR retires.
2. **It brings the two Minnesota priors into agreement.** `NIWPrior`, the conjugate engine, has scaled by this same `sigma` since it was written — `minnesota_dummies` takes `sigma` as a required argument. Before this change, fitting the same model through `VAR(prior=MinnesotaPrior())` and `ConjugateVAR` encoded two different beliefs about a cross-variable coefficient whenever the variables' scales differed, for no principled reason — one path used the textbook ratio, the other used 1.
3. **ADR-0012 precedent.** ADR-0012 made the identical argument for `B_exog` and named this exact gap as a tracked follow-up: *"the two priors do not yet speak in one language... adopting that scale here is a step towards it, not a claim that it has happened."* This closes that follow-up. As with ADR-0012, the library is pre-v0.1 and the old numbers were silently wrong for any model with variables on different scales — a warning in the docs is not a fix, it is a workaround that only the user who reads the docs benefits from.

**This is a bigger break than ADR-0012 took, and that is a deliberate, separate decision.** ADR-0012's `exog_prior_scale` is a plain field on `VAR`; it changed no protocol and broke no third-party `Prior`. ADR-0012 also *considered* widening `Prior.build_priors(n_vars, n_lags)` with an exogenous block and rejected it, precisely because that widening would break every third-party `Prior` for a term (`B_exog`) that most priors have no opinion about and that is not Minnesota-shaped. This ADR does the widening ADR-0012 declined — `sigma` is now a required argument, and any third-party `Prior` implementing only `(n_vars, n_lags)` breaks. That is not a reason to avoid it here; the two cases differ in what's being added. `B_exog` is a term bolted onto `build_priors` from outside — most priors never touch it, `MinnesotaPrior` doesn't compute it, and giving `build_priors` an opinion about it would be adding a concept the seam does not own. `sigma` is not a new concept: it is additional context for the one thing every `Prior` implementation already produces — `B_mu`/`B_sigma` for the lag block, the entire reason the protocol exists. A prior with no use for the data's scale can accept and ignore `sigma`, the same way it could always ignore `n_lags` if it did not care about lag order; there is no analogous "ignore it" escape hatch for a whole exogenous-coefficient block a prior was never designed to speak to.

## Considered options

- **A switch, or a required flag defaulting to off** — rejected. The unscaled prior is not a legitimate alternative belief the way, say, `decay="geometric"` vs `"harmonic"` are; it is a units bug. A flag defaulting to off ships the bug by default and asks users to know to turn on the fix; a flag defaulting to on is just this change with extra surface area. `exog_prior_scale` earned its knob because looser-vs-tighter is a real modelling choice; `sigma_i/sigma_j` is not.
- **Scale `B_sigma` in `spec.py`, outside the prior** — rejected on its own terms: `spec.py` does not know which columns of a `Prior`'s `B_sigma` are "cross" versus "own" — that mapping is internal to how each `Prior` lays out its coefficient block, and `MinnesotaPrior` is not the only implementation the registry has to support. Multiplying by a ratio matrix built from `col_var` assumptions that belong to `MinnesotaPrior` from outside it would silently do the wrong thing to any third-party `Prior` with a different layout, and would rescale a flat or zero-mean custom prior that never asked to speak in Minnesota's cross/own vocabulary. The scaling belongs where the cross/own structure is already known: inside `build_priors`. (This is a different objection from ADR-0012's rejection of an exogenous block on the protocol — that one turned on `B_exog` being a term `Prior` does not own at all; this one turns on `spec.py` not knowing a layout `Prior` already owns internally.)
- **Leave the protocol alone; special-case `MinnesotaPrior` with an `isinstance` check in `spec.py`** — rejected. This is the shadow-protocol anti-pattern ADR-0013 removed from the identification seam: a second, undeclared contract (`MinnesotaPrior` gets data, everyone else doesn't) that `isinstance` branching hides from the `Prior` Protocol itself. It would also mean `VAR.fit` could never pass `sigma` to a third-party Minnesota-shaped prior without `spec.py` knowing its class by name.

## Consequences

- **Breaking**: every posterior fitted through `VAR.fit(prior="minnesota", ...)` (the default) with **more than one endogenous variable** changes, because every cross-lag prior standard deviation is now scaled by `sigma_i / sigma_j` instead of 1. Single-variable VARs are unaffected — there are no cross-lag terms, and the own-lag ratio is 1. This is pre-v0.1; the old numbers were unit-dependent in a way nothing in the output flagged, exactly the class of change ADR-0012 already accepted for `B_exog`.
- **Breaking**: the `Prior` protocol's `build_priors` gains a required keyword-only parameter, `sigma`. Any third-party `Prior` implementation that only accepts `(n_vars, n_lags)` now raises `TypeError` when `VAR.fit` calls it. A prior with no use for the data's scale still has to accept and ignore the argument — see `docs/how-to/custom-priors.md` for the updated minimal example.
- Keying `MinnesotaPrior` off `sigma` newly exposed it to the same degenerate-endogenous-column failure ADR-0012 flagged for `B_exog`, and a near-zero `sigma_c` (variable `c` constant or numerically flat) breaks it in more than one place at once: (1) every cross-lag entry in row `c` — the constant variable's own equation, regressing on other variables' lags — has `sigma_c` in the *numerator* and collapses toward zero, over-shrinking a row of the prior that was never the reason the column was constant; (2) every cross-lag entry in every *other* equation's row that regresses on variable `c`'s lag has `sigma_c` in the *denominator* instead, and blows up — for a numerically near-constant (but not exactly constant) column, `sigma_i / sigma_c` can reach `1e12` or more for otherwise ordinary data, an effectively flat, uninformative prior on that coefficient in every equation but `c`'s own; (3) if `sigma_c` is *exactly* zero, the blow-up in (2) is literally `inf` (`ar1_residual_sd`'s own floating-point arithmetic rarely lands on exact zero, but a directly supplied `sigma` — e.g. from the caller-supplied-`sigma` seam described below — easily can), and the own-lag entry (`i == j == c`) is `0.0 / 0.0`, which is `nan`, **not** `1`. "Own lags are untouched, since the ratio is 1" (stated above and in the `MinnesotaPrior.build_priors` docstring) holds only while `sigma` is finite and nonzero; an exactly-zero `sigma_c` breaks that silently, for the one row it looks like it should protect most. **Guarded now (issue 07b)**: `VARData` rejects endogenous columns that are exactly constant over the whole sample, the same way it already rejects exactly-constant `exog` columns; `VAR._build_pymc_model` additionally rejects a zero, negative, or non-finite entry in the `sigma` it computes, catching the rarer column that varies but is nonetheless perfectly predictable from its own first lag (a short, noiseless sample, say), so `ar1_residual_sd` still returns exactly zero for it; and `MinnesotaPrior.build_priors` itself rejects a zero, negative, or non-finite entry in a directly supplied `sigma`, for callers who bypass `VAR.fit` and call it themselves. A numerically near-constant but genuinely varying column is left alone — the blow-up in (2) is accepted, not floored, because it is still finite and the column is still a real, identified variable.
- `B_mu` is unchanged — this ADR touches `B_sigma` only.
- `_build_pymc_model` now computes `ar1_residual_sd(data.endog)` exactly once per `fit`/`prior_predictive` call and shares it between the lag-coefficient prior and `_exog_prior_sigma`, which previously recomputed the same quantity internally. `_exog_prior_sigma`'s first parameter changed from the raw endogenous array to the precomputed `sigma`, purely an internal seam; it is not part of the public API.
- A later issue may let callers supply their own `sigma` (e.g. a scale estimated outside the sample, or held fixed across a rolling re-fit) instead of always deriving it from `ar1_residual_sd(data.endog)`. Both `Prior.build_priors` and `_exog_prior_sigma` already take `sigma` as a plain array, not a data-derived computation, so that seam needs no further widening — only a new argument on `VAR` to override the default.
