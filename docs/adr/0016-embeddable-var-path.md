# A VAR can be embedded in a larger PyMC model, and latent series in it are non-centred

`VAR.build_in_model` registers a VAR into whatever `pymc.Model` is active when it is called: the intercept, the lag coefficients `B`, the exogenous coefficients `B_exog`, the volatility process's latents and the observation likelihood. It returns a `VARModelHandles` holding the intercept, `B`, `B_exog`, the Cholesky factor `L` and the likelihood term `obs`, plus `latent` and `latent_names` when there are latent series. The volatility process's own latents are reachable only by name. It is the only code that builds a VAR graph. `_build_pymc_model`, which `fit` and `prior_predictive` both call, is a thin wrapper around it: it resolves a string `lags` with `select_lag_order`, opens a fresh `pm.Model` with a `time` coordinate taken from `data.index`, and passes `VARData`'s arrays to `build_in_model`. So there is one model, and fitting it standalone and embedding it describe the same density. `FittedVAR.from_posterior` is the other half of the seam. It checks a posterior against the schema `VAR.fit` and `ConjugateVAR.fit` both produce, then wraps it, and both estimators build their result through it. It is the one supported way to turn a posterior into a `FittedVAR`. The only other way is pydantic's `model_construct`, which skips validation. It checks variables by their exact, unprefixed names against a `VARData`, so an embedding caller must first return its posterior to the schema (see Consequences).

The motivating caller is a marketing-mix model whose baseline is a VAR-shaped latent series (pymc-marketing's `VARBaselineEffect`). Nothing in this ADR depends on that caller.

**Namespacing is PyMC's, with its gaps.** `build_in_model` takes no prefix argument. A caller that wants namespacing opens `pm.Model(name=prefix)` first, and every free random variable, `Deterministic` and `Potential` Impulso registers comes out as `prefix::...`. The prototype confirmed this, including with `pymc.dims` around the nested model. PyMC does not prefix two things:

- **Coordinates.** `var`, `var1`, `var2`, `coeff`, `exog` and `var_intercept` land on the root model and are shared by every submodel. Identical labels are shared silently, and different labels raise PyMC's `Duplicate and incompatible coordinate`. A model can therefore hold only one embedded VAR per variable labelling. `time` is a coordinate too, and `add_coords` only rejects a duplicate whose values differ, not one whose length differs. `build_in_model` therefore checks an existing `time` coordinate's length against its own `T - n_lags` and raises if they differ. When the length of a symbolic `endog` is unknown (a `pm.Data` or `pytensor.shared` value), it registers and checks no `time` coordinate: its likelihood is a `Potential`, which has no dims.
- **`pymc.dims.Data`.** A `pmd.Data` created inside a nested model is not prefixed, although `pm.Data` is. Impulso creates no data containers, and a caller must not rely on the nested model to namespace one it creates.

**Symbolic observed `endog`.** `endog` may be a 2-D PyTensor variable, such as a `pm.Data` container the caller owns (a dimmed `XTensorVariable` is refused; pass its `.values`). A symbolic value cannot be an RV's `observed`, so the likelihood is `error_dist.logp(mu, chol, value)` wrapped in a `pm.Potential` named `obs`. At the same point it gives the same density as the observed RV of the numpy path. Each `ErrorDistribution` adapter implements `logp` with its own PyMC distribution, so the ADR-0007 scale-matrix convention carries over unchanged. **`obs` is then not a random variable. It has no dims, and neither `sample_prior_predictive` nor `sample_posterior_predictive` can see it or draw it.** The numpy-only steps are skipped. `ar1_residual_sd` needs concrete data, so `endog_scales` becomes required. It feeds both the Minnesota cross-lag ratio σᵢ/σⱼ ([ADR-0015](0015-minnesota-cross-lags-scale-with-data.md)) and the exogenous prior ([ADR-0012](0012-exog-prior-scales-with-data.md)). It is shape-checked against `n_vars` and must be finite and strictly positive. Its error messages name `endog_scales` as the source, not `ar1_residual_sd`, which never ran on this path. The volatility process gets `data=None` in place of OLS pre-fit residuals.

**Latent series are generated, not passed in.** `latent_names` declares endogenous series with no data. They come first in `endog_names`, and `endog` holds only the observed columns that follow them. `endog_scales` is then required and must cover the latent series too. Passing one scale per observed column raises an error that says so. Each latent path is generated inside the model, non-centred:

```
latent_init[l, k]        ~ Normal(0, latent_init_sigma[k])        # first n_lags values
latent_innovations[t, k] ~ Normal(0, 1)                           # z, t = n_lags .. T-1
latent_t = c_lat + Σ_l A_l[lat, :] full_{t-l} + B_exog[lat] x_t + L[lat, lat] z_t
```

Here `full` stacks the latent path with the observed columns. The terms that do not depend on the latent path are computed in one vectorised step. `scan` carries only the latent-on-latent recursion. The path, including its initial values, is the `Deterministic` `latent`, returned as `handles.latent`. After the first `n_lags` values the VAR is the latent series' only prior.

The latent series lead the Cholesky ordering, and `L` is lower-triangular ([ADR-0014](0014-manual-cholesky-parameterisation.md)). The observed block's likelihood conditional on `z` is therefore exact:

```
resid_obs − L[obs, lat] z  ~  MvN(0, L[obs, obs] L[obs, obs]ᵀ)
```

It is evaluated with `error_dist.logp` on that sub-block and registered as the `Potential` `obs`. Under `Constant`, row 0's diagonal entry is exactly that variable's innovation standard deviation, and the first latent series is row 0. A per-variable `innovation_scale_priors` entry on it therefore means what it says.

The reason is the prototype's funnel. The first design passed a free latent column in as symbolic `endog`, with the VAR likelihood as a `Potential`. That design gave 70, 86, 94, 97, 116, 637 and 932 divergences per 4000 draws on seven seeds. 73–99% of them fell in the lowest posterior quintile of the latent innovation scale σ_b, and corr(log σ_b, path roughness) was +0.80. Two seeds each had a chain stuck in the neck of the funnel, with R-hat 1.29–1.62 and bulk ESS 7–11. A zero-avoiding Gamma(2) prior on σ_b still gave 62 and 824 divergences. The non-centred form with a stationary start gave zero divergences on six of seven seeds, and 76 in one burst in one chain on the seventh. Scan added no noticeable sampling cost.

**Latent own-lag prior mean.** `latent_own_lag_mean` replaces the Minnesota prior mean of each latent equation's own first-lag coefficient. The observed equations keep the prior's mean. The default of 1 leaves the Minnesota prior as it is. **A caller modelling a stationary deviation passes 0**, because a random-walk prior mean is the wrong belief for such a series. The prototype's follow-up changed only this mean, from 1 to 0, on the non-centred design across the same seven seeds. Total divergences fell from 76 to 8, max R-hat was at most 1.057, and the worst seed's minimum bulk ESS rose from 34 to 78. The loading's downward bias shrank only a little (posterior mean 0.42–0.44 → 0.46–0.48 against a truth of 0.6). Under the default nutpie initialisation, the seed that froze a chain at an own-lag of 1.58 under mean 1 sampled cleanly under mean 0, but that is one seed.

**Stationarity of the latent block.** An explosive draw of the latent coefficients makes the generated path explode over the sample, and in the prototype that froze a chain (step size about 1e−278). Three things guard against it:

- **Initial values.** The model's initial point starts every latent equation at an own first lag of 0.5, with every other coefficient in the latent rows at 0. PyMC sets an initial value for `B` as a whole, so the observed rows start at their prior mean, which is PyMC's default start anyway. The sampler's jitter moves this start, and the Potential below is what rejects a jittered start that lands outside the region.
- **The `latent_stationarity` Potential.** It is 0 when the spectral radius of the companion matrix of the latent-on-latent block (latent rows, latent lags, all `n_lags`) is below 1, and −∞ otherwise. The observed series are data, so this block alone decides whether the path explodes. `B` stays a single `Normal`, so **the posterior is the prior truncated to the stationary region of the latent block.** A jittered start outside the region has −∞ log density, and PyMC redraws it. The Potential is piecewise constant, so its gradient is zero. PyTensor cannot differentiate the complex `eig`, and PyMC's rewrites strip `disconnected_grad`. The radius is therefore an `OpFromGraph` whose gradient is overridden with zeros (through `pullback`, or `lop_overrides` on older PyTensor). `eig` raises on a non-finite matrix, which would abort the sampler rather than record a divergence. A non-finite companion matrix is therefore swapped for `2·I` first, so the Potential is −∞.
- **What it does not do.** A Potential is not a random variable, so `sample_prior_predictive` ignores `latent_stationarity`. Prior-predictive latent paths come from the untruncated prior and can still explode. If the latent own-lag prior mean is near 1 and the data want persistence near 1, the posterior presses against the boundary and diverges there. On the 09b test setup with the default mean of 1, 212–290 of 400 draws diverged. That is one more reason to pass 0 for a stationary deviation.

`latent_init`, `latent_innovations` and `latent` have no dims. A latent coordinate would be unprefixed and would collide between two VARs in one model, so the names travel on `handles.latent_names` instead, in the path's column order.

**`intercept_equations`** names the equations that get an intercept. `None` means all of them, which is the graph from before the argument existed. A strict subset gets its own `var_intercept` coordinate (in `endog_names` order, unprefixed like the rest), scattered into a length-`n_vars` vector with literal zeros. An empty sequence registers no intercept, and `handles.intercept` is `None`. An excluded equation has no intercept term at all, so its series is a zero-mean deviation around a level owned elsewhere in the model. That is how a latent baseline sits under the host model's own intercept.

**Rejections.** On the embedded path, meaning a symbolic `endog` or any latent series, `build_in_model` refuses three things. It checks them before registering anything, so a refused call leaves no partly built model behind:

- **A string `lags`.** Lag selection runs OLS on concrete data, and there is none. The caller resolves the criterion first, for example with `select_lag_order`.
- **Any volatility process other than `Constant`.** Stochastic volatility seeds its priors from OLS residuals of concrete data.
- **Non-Gaussian errors with latent series.** The conditional of a multivariate Student-t is not a Student-t with the same `nu`, so the non-centred conditional likelihood has no simple closed form. A symbolic observed `endog` with no latent series may still use Student-t errors, because it needs only the joint `logp`.

`single_unit_root` and `sum_of_coefficients` exist only on `NIWPrior`, which only `ConjugateVAR` uses, so they need no rejection here.

## Considered options

- **Centred latent series with a `Potential` likelihood** — rejected. The caller passes a free latent column as symbolic `endog`, and the VAR logp constrains it. The prototype's evidence rules it out. It is a funnel in the latent innovation scale, with divergences on every seed. A zero-avoiding scale prior did not remove it.
- **The conjugate route** — not needed. A closed-form marginal likelihood as a `Potential`, using `ConjugateVAR`'s machinery, would remove the coefficients from the sampler. The PRD set it as the remedy for *coupling*, meaning poor mixing along coefficient/latent ridges. The failure was a funnel. Divergent draws were displaced in log σ_b by −1.9 SD but in the loading by only +0.35 SD. corr(loading, own-lag) was −0.98 in every variant, and divergences did not sit along that ridge. The ridge does limit ESS (about 40–135 in the non-centred runs) and is the thing to watch if mixing becomes the problem.
- **A bounded own-lag variable** (e.g. `tanh` or a stationarity-respecting transform of the latent block) — rejected. For one latent series at VAR(1) a `tanh` bound on the own lag does bound the spectral radius, so there the rejection rests on cost alone. With cross-lags between latent series or `n_lags > 1`, bounding each own lag no longer bounds the radius, and only a full stationarity-respecting transform of the latent block would. Either way the costs are real. The latent rows' prior is no longer the Minnesota `Normal` that every other row gets, and the transform adds free variables. `B` could be reassembled as a `pm.Deterministic("B", dims=("var", "coeff"))`, so the posterior schema would survive. But `handles.B` would then be a Deterministic, and PyMC's initial point covers only free variables, so a `set_initval` on it would be silently ignored. The stationary start would have to move onto the underlying variables. A single `Normal` truncated by a Potential avoids all of this. It costs boundary divergences only when the posterior sits near the boundary, which the default own-lag mean of 1 makes likely.
- **Sampler-only guidance** — rejected. It means documenting that callers should initialise inside the stationary region, and doing nothing in the graph. Under nutpie's default initialisation the jitter started a chain outside the stationary region. The chain froze at an own-lag of 1.58 with 1000 divergences and R-hat 1.59, and the loading HDI excluded the truth. Guidance does not reach the caller who never reads it, and `build_in_model` knows exactly which rows need a stationary start.

## Consequences

- `fit`, `prior_predictive` and embedding callers share one graph. A change to the VAR's priors or likelihood reaches all three, and a test pins that the wrapper and a direct call give the same log-probability.
- **The embedded path's `obs` is invisible to predictive sampling.** On a symbolic `endog` or with latent series, neither `pm.sample_prior_predictive` nor `pm.sample_posterior_predictive` draws the observed block. Prior-predictive checks there cover only the free RVs and the `latent` and `Sigma` Deterministics. `FittedVAR.posterior_predictive` computes in NumPy ([ADR-0011](0011-posterior-predictive-computed-in-numpy.md)) and needs a `VARData`, which a latent series does not have.
- **Coordinates are shared across nested models.** Two embedded VARs in one model must have the same variable labels and the same `T - n_lags`, or must live in separate models.
- **The Student-t latent path is unsupported.** Lifting it needs a conditional likelihood for the observed block given the latent innovations under a multivariate t. That is a new `ErrorDistribution` capability, not a flag.
- **The JAX backend is barely exercised, and JAX on GPU not at all.** The spectral radius uses a nonsymmetric `eig` inside an `OpFromGraph`. It is tested on the PyMC (C) and nutpie (numba) backends. A JAX test compiles logp and dlogp, but it skips when JAX is not installed. Nothing tests `eig` on a GPU, where JAX's nonsymmetric eigendecomposition support is limited.
- Latent-scale priors still matter for mixing. With the default `HalfCauchy` diagonal, the latent scale and its loading form a ridge (about 8% divergences in issue 09c's tests). A tighter per-variable prior through `Constant.innovation_scale_priors` is the lever, and the first latent series is the one variable whose diagonal prior is exactly its innovation standard deviation.
- `from_posterior` is now the gate for every `FittedVAR` an estimator returns. For an embedding caller it is the gate for a posterior that the caller has returned to the schema. The caller must strip the nested-model prefix from the variable names, and must supply a `VARData`. With latent series that means filling in a plug-in column for each latent series, such as the posterior-mean latent path, which is what pymc-marketing's `fitted_var` will do. The schema check is then the same one Impulso's own estimators get.
